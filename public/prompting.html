Prompt Engineering

Write clearer prompts and check the results.

A useful prompt describes the task, provides relevant material, and sets criteria for the result. This guide gives you a structure to reuse, examples to adapt, and ways to check whether a change improves the output.

Jump to the framework → Get hands-on training
The Problem

Why most prompts fail

When you ask a model to “write a summary” without specifying the audience, length, or relevant points, it has to infer those choices. State them directly so you can evaluate the response against what you asked for.

Clear instructions reduce ambiguity, but they do not guarantee a correct response. Models can still omit details or produce errors. Specify what to do when information is missing, then review the result.

Save prompts for recurring tasks such as weekly summaries, client email drafts, or data extraction. Test them on several representative inputs and keep notes on failures. A shared library lets your team improve and reuse the instructions, while still checking each result.

"A prompt is a contract with the model. The clearer the contract, the more reliable the result."
The Framework

The CRAFT Framework

RUDI’s CRAFT checklist covers five decisions: the context, role, action, format, and tone. Use it to make your request specific enough to test.

C
Context

What background does the model need? What's been tried? Who's the audience? Without context, the model defaults to generic.

R
Role

"Senior security engineer reviewing a PR" produces different output than "code reviewer." Roles prime vocabulary and judgment.

A
Action

What exactly should the model do? Verb + object + for-whom. "Summarize" is vague; "extract decisions and action items for a Slack post" is actionable.

F
Format

How should the output be structured? Bullets / JSON / sections / length / fields. Specify the shape you need so you can check whether the response follows it.

T
Tone

Voice, register, formality. "For a CFO in 30 seconds" vs "for a teammate over coffee" — same content, different prompt.

CRAFT covers the five decisions you have to make. The next section shows where they sit inside the full anatomy of a prompt.

Deep Dive

The anatomy of a prompt

You can extend CRAFT with the source material the model should use and examples of the result you want. Include the parts that the task needs.

Slot What it does CRAFT
Role Who the model is playing R
Task The explicit directive A
Context Why this matters, constraints, audience C
Input The actual material being operated on — the document, data, or text the model works with + add
Examples Input → output demonstrations that lock the format and style + add
Output Format Shape, length, schema F
Tone Voice and register T

Input (delimited content) is the piece most people forget to make explicit. When your instructions and your data look the same — both just plain text in a row — the model can lose track of which is which. Wrapping your input in XML tags, triple backticks, or a --- block creates a clear boundary. This matters most when the input is long, when it contains instructions of its own (like a pasted email), or when you're chaining multiple steps.

Examples show the format or style you want the model to follow. Include a representative input and output when a description leaves too much open to interpretation, then test whether the example helps on other inputs.

Techniques

Seven techniques to test in your prompts

Try these techniques where your prompt is unclear or the output is inconsistent. Compare results on the same set of tasks before keeping a change.

01 Specificity

Make criteria specific enough to check. For example, replace “concise summary” with “three bullets covering decisions and action items, under 80 words.” Include an example when tone or style matters.

Before
"Write a concise summary of this meeting."
After
"Write a 3-bullet summary of this meeting transcript. Focus only on decisions made. Each bullet ≤20 words. For a CFO who has 30 seconds."
02 Structure & Delimiters

Separate your instructions from your data. The model gets confused when they look the same. Use XML tags, triple backticks, or --- blocks. Pick one style and use it consistently across all your prompts — it builds a habit the model can recognize.

Before
"Summarize this email: Hi team, just wanted to follow up on..."
After
"Summarize the email below.

<email>
Hi team, just wanted to follow up on...
</email>"
03 Examples (Few-Shot)

Show an input and the output you want, especially for structured extraction or an unfamiliar format. Test the prompt on different examples to check that it can handle variation.

Before
"Extract the action items from this transcript in a useful format."
After
"Extract action items in this exact format:
- [ ] [action] — @[owner] — [due date or 'TBD']

Example:
- [ ] Send Q3 deck — @sarah — Friday"
04 Output Contract

Specify the exact shape: JSON schema, field names, types, length, allowed values. Then add a fallback for when the model can't comply. Without a fallback, the model invents an answer rather than admitting uncertainty — and the invention looks indistinguishable from the real thing.

Before
"Tell me what's in this contract."
After
"Extract these fields from the contract as JSON:
{parties: string[], effective_date: string, term_months: number, termination_clause: string}
If a field is missing, use null.
If the document isn't a contract, respond with:
{error: 'not a contract'}"
05 Role / Persona

A role can help specify the perspective and vocabulary you want. Pair it with concrete review criteria so you can check whether the response addresses the task.

Before
"Review this Python function."
After
"You are a senior backend engineer reviewing a junior teammate's pull request. Be direct but constructive. Focus on: correctness, readability, error handling. Skip style issues a linter would catch."
06 Reasoning Trigger

For multi-step problems, ask the model to think before answering. "Think step by step before responding" works on most models. On Claude's extended thinking mode or OpenAI's o-series reasoning models, skip this — they already reason internally, and explicit chain-of-thought instructions can actually hurt performance.

Before
"What's the best pricing strategy for our SaaS product?"
After
"Think step by step before answering:
1. What pricing models are common in SaaS?
2. Which fits a tool with our usage profile [see below]?
3. What are the trade-offs?

Then recommend ONE model with reasoning."
07 Grounding

For anything factual, paste the reference text inside the prompt and constrain the model to it. This is the single highest-impact move for reducing hallucination. Without grounding, the model draws on training data that may be wrong, outdated, or simply absent for your specific context.

Before
"What does our refund policy say about international orders?"
After
"Refund policy:
<policy>
[paste full policy here]
</policy>

Question: What does the policy say about international orders?
Answer using ONLY the text above. If it isn't covered, respond:
'Not specified in current policy.'"
Ready to Use

Ready-to-use templates

Six templates for common tasks. Fill in the brackets, try each one on representative input, and review the result before using it in your workflow.

1 — Summarize (meeting / doc / email)

You are a [audience-appropriate role, e.g., "executive assistant"].
Summarize the content below for [specific audience: "the engineering team in a Slack post"].

<content>
{{paste here}}
</content>

Produce exactly:
**Key points** — 3 bullets, ≤20 words each
**Action items** — bulleted, each with owner and due date (or "TBD")
**Decisions** — bulleted, or "_None_"

Skip pleasantries. Only include items explicitly stated.

2 — Extract structured data

Extract the following fields from the text below as JSON.

Fields:
- [field_name]: [type] — [description]
- [field_name]: [type] — [description]

<text>
{{paste here}}
</text>

Rules:
- Return ONLY valid JSON, no commentary
- Use null for missing fields
- If the text doesn't match the expected type, respond with:
  {"error": "input does not match expected format"}

3 — Draft (email / message / copy)

You are writing on behalf of [sender]. You are [relationship to recipient].

Write [type, e.g., "an email"] to [recipient] about [topic].

Tone: [specific: "warm but direct", "formal", "casual peer-to-peer"]
Length: [bounded: "≤150 words"]
Goal: [what should happen after they read it]

Constraints:
- Do NOT [common pitfalls: "apologize", "use corporate jargon", "include emojis"]
- DO [must-haves: "include a clear next step", "reference our last conversation"]

Context they need:
{{any background}}

4 — Decide (compare options & recommend)

You are advising me as [role: "a strategic consultant", "a senior engineer"].

I'm deciding between these options:
A) [option A]
B) [option B]
C) [option C]

My situation:
{{relevant context, constraints, goals}}

Walk through:
1. The decisive trade-offs (not all of them — just the ones that matter here)
2. Your recommendation with reasoning
3. The conditions under which you'd change your recommendation

Be direct. Skip the diplomatic hedging.

5 — Critique (feedback on work)

You are a [domain expert, e.g., "senior product designer"] giving honest feedback to a colleague.

Review the [artifact, e.g., "wireframe", "draft", "code"] below.

<artifact>
{{paste here}}
</artifact>

Structure your feedback as:
**What's working** — 2-3 specific strengths
**What's not** — 2-3 specific issues, with WHY each matters
**Highest-leverage change** — the single edit that would most improve it

Be specific. "This is unclear" is useless — say what's unclear and why.

6 — Teach / Explain

You are explaining [topic] to [audience: "a smart non-expert", "a new hire on the team"].

Their starting knowledge: [what they already know]
What they need to be able to do after: [concrete outcome]

Structure:
1. The one-sentence version
2. The mental model (analogy or core concept)
3. The detail they need (only what serves the outcome — skip everything else)
4. A worked example
5. What's NOT covered (so they know the limits)

Keep it under [length]. Use plain language. No jargon without immediate definition.
Model-Specific

Tips by AI model

The universal anatomy works everywhere, but each major model has quirks worth knowing.

Claude
Anthropic
  • Loves XML tags for structure (<instructions>, <context>, <document>) more than other models
  • For long documents, put the document FIRST and your question LAST — Anthropic cites ~30% quality improvement with this ordering
  • Use the extended thinking / effort budget for hard reasoning instead of writing "think step by step"
  • You can prefill the assistant's response to lock format — useful for guaranteed JSON or structured output starts
GPT
OpenAI
  • Strong with structured outputs — use the JSON schema feature when available rather than describing the shape in prose
  • For o-series reasoning models (o1, o3): skip chain-of-thought prompts — they already reason internally and explicit CoT can hurt
  • Repeat critical instructions at the END of long prompts — recency bias is real and well-documented
  • Build a small eval set early — OpenAI's own docs treat systematic testing as core to prompt engineering, not optional
Gemini
Google
  • Pay attention to sampling parameters (temperature, top-K) — Google treats them as part of prompt design, not an afterthought
  • Try "step-back prompting": ask a more abstract version of your question first, then apply the answer to the specific case
  • For high-stakes reasoning, run the same prompt multiple times and take the majority answer — self-consistency works well here
Anti-Patterns

Seven common prompting problems

Check these points when an output misses your requirements.

  1. Vague adjectives instead of measurements. "Concise," "professional," "good" — these tell the model nothing. Replace with numbers, examples, or named comparisons.
  2. No examples for novel formats. If the format is anything other than plain prose, show one example. Description is not enough — demonstration is.
  3. No fallback for "I don't know." Without an out, the model invents an answer. Always include: "If you can't, respond with exactly: [phrase]."
  4. Asking for five things in one prompt. Models get worse with each additional task in a single shot. Split into chained prompts or accept reduced quality on all five.
  5. Burying instructions in long context. Recency bias is real — the model weights the end of the prompt more heavily. Restate critical instructions at the bottom.
  6. No negative space. "Do NOT explain your reasoning." "Do NOT apologize." "Do NOT include caveats." Models over-help by default — explicitly say what you don't want.
  7. Changing prompts without checking the results. "Better on the one I tried" is how prompts silently regress. Build a 10-example test set and run all 10 every time you tweak.
FAQ

Frequently asked questions

What is the best prompt framework?
CRAFT is RUDI’s checklist for Context, Role, Action, Format, and Tone. It helps you specify the task and the result you want. Add source material and examples where they help, then test the prompt on representative inputs.
What's the difference between a system prompt and a user prompt?
A system prompt sets persistent instructions for the entire conversation — role, tone, constraints, output format. A user prompt is the specific request in a turn. Best practice: put role, format, and constraints in the system prompt; put the task and input in the user prompt.
How is prompting Claude different from prompting GPT?
Claude responds particularly well to XML tags as structure (<instructions>, <document>). For long context, Claude prefers the document at the top and the question at the bottom. GPT's o-series reasoning models actually do worse with explicit "think step by step" instructions — they already reason internally. Gemini benefits from "step-back prompting" (asking an abstract version of the question first). Universal principles work everywhere; these are optimizations on top of that foundation.
Do I need examples in every prompt?
No. Examples (few-shot prompting) are most valuable when (a) you want a specific format, (b) the output is structured or unusual, or (c) you've tried without examples and the output isn't matching your intent. For simple, well-known tasks like summarization, examples often aren't needed.
How long should a prompt be?
Include enough context, instructions, and examples to make the task clear. Test a shorter version if it contains repetition. Keep the detail that improves results on your actual inputs.
Why isn't my prompt working?
Check whether the task is clear, the required information is present, and the expected format is specified. Try a representative example and say how to handle missing information. If problems persist, review whether the model and workflow fit the task.
What's the difference between zero-shot and few-shot prompting?
Zero-shot means you ask the model to do something without showing examples. Few-shot means you include one or more input→output examples in the prompt. Few-shot is more reliable for unusual formats or specific styles; zero-shot is fine for common tasks the model has seen during training.
How do I prevent the AI from making things up?
Provide relevant source material, ask the model to distinguish supported information from gaps, and verify important claims against the sources. These steps can reduce errors, but no prompt guarantees a factual response.
